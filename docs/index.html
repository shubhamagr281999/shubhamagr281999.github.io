Physical-AI infrastructure for VLA manipulation

Apr 2026 – present · Miko

Built the loop that turns raw teleoperation into a trained manipulation policy: curate, fine-tune, then evaluate in simulation or on real arms through the same code path. The hard part was making a slow policy degrade smoothness instead of breaking the control loop.

Problem

The models are open source. Almost nothing between "a teleoperator moved the arms" and "a trained policy runs on hardware" is. Raw recordings are not a training set, there was no way to run a candidate policy repeatably against varied scenes, and nobody had read the candidate architectures, π₀.₅ and OpenVLA-OFT, closely enough to say which engineering constraints were real.

Approach

Three layers that close into a loop. A desktop curation tool over the LeRobot dataset format that browses every episode across many datasets, trims them against a film-strip, rebalances the task mix, and runs a live quality report before you pay for a build. A backend-agnostic runner where one control path drives either a MuJoCo scene or the real arms, chosen by a config key, with scene randomisation, goal predicates, a geometric safety gate and remote GPU inference. And underneath both, operation-level traces of both candidate architectures, π₀.₅ and OpenVLA-OFT, verified against live instrumented runs rather than read off the papers.

Outcome

Preview went from a blocking per-frame decode to about 150 ms, roughly 45 times faster, by handing video to the viewer instead of decoding it in Python. A representative dataset build dropped from around 600 seconds to 27. The live quality report recomputes in about a millisecond, so it guides curation instead of describing the result afterwards. The OpenVLA-OFT forward trace passed 18 of 18 checks against a live run, correcting three values in my own draft along the way.

Production autonomy stack for an indoor mobile robot

Jul 2023 – present · Miko

Three years on one robot, across every layer of it: the sysfs GPIO driver that moves the wheels, the shared-memory bus that carries the odometry, and the TSDF mapper and planners that decide where to go. The mapping backend was replaced mid-life without touching the planners.

Problem

An indoor robot has to navigate an environment nobody surveyed in advance, keep a usable map of it across power cycles, avoid things that move, and do all of it on a mobile SoC with no ROS on board and a real power budget. Holding those layers together is a different problem from solving any one of them.

Approach

At the bottom, a Yocto distribution for a Qualcomm SoC with cross-compilation and device-tree work, then a hardware abstraction layer over GPIO, PWM, encoders, I2C and UART, with a co-processor firmware and a PID drive system on IMU-fused odometry. In the middle, a ROS-free publish/subscribe and service bus over shared memory, with a process manager and a watchdog. On top, TSDF submaps carrying occupancy and distance in one voxel, a pose-anchored submap collection that consumes optimised poses from the team's SLAM, D* Lite for global planning and a DWA local planner with a behaviour layer over it.

Outcome

A deployed robot that maps, plans, explores and persists its map across power cycles. I authored the seven-stage CI pipeline that gates it, including a performance-regression stage: an in-house profiler times instrumented functions to CSV, and the pipeline pulls the baseline from the package registry and plots each change against it. That is why the optimisation work is verifiable rather than asserted.

Running a learned model on a robot's NPU

Oct – Dec 2025 · Miko

A person-following capability with the detector running on the robot's Hexagon DSP. Detecting people is the easy half. Knowing that the person in frame now is the same person you were following a second ago is the half that decides whether it works.

Problem

Following a person needs a detector fast enough to run continuously on a power-constrained mobile SoC, a way to hold onto the right person across frames when other people walk through, and a motion estimate good enough to keep going when the detector misses.

Approach

A person-landmark network runs on the DSP through the vendor's neural network SDK, with the backend and model both loaded dynamically from config so the model can change without a rebuild, and tensors built by deep-copying the graph's own descriptors so shapes and dtypes follow the model instead of being hard-coded. Detections are thresholded and passed through a hand-written non-maximum suppression. Foot landmarks project to a ground position through the depth image, an HSV histogram gives an appearance model, and association scores squared distance plus a weighted appearance term. A templated, allocation-free Kalman filter carries the target through detection gaps.

Outcome

Shipped as a real capability, with the follow distance, search pattern, extrapolation window and association weighting all configured rather than compiled in. Because the detector sits behind an interface with a dummy implementation, the tracking and behaviour layers run and are testable with no DSP and no robot present.

Control and simulation of a soft continuum robot

Aug 2022 – Jun 2023 · Master's thesis, IIT Bombay

A five-segment silicone robot I fabricated, closed-loop controlled from an overhead camera. My controller needed torque and the servos could not deliver it, so I cast a torque sensor from the same silicone as the robot. Then that failed too, and the fix was to change what the controller commands.

Problem

Soft robots deform continuously, so their state is effectively infinite-dimensional. The models accurate enough to trust are too slow to sit inside a control loop, and the models fast enough to run in the loop are only valid for slow motion and specific shapes. I wanted one model that was both fast enough to close a loop and accurate enough to be worth closing.

Approach

I represented the planar body as a mass-spring network whose stiffness matrix is rebuilt from the deformed configuration every step, which is what captures geometric nonlinearity at large deflection without paying finite-element cost. I validated it against analytical solutions, a chained beam-constraint model and FEM, then built a predictive controller on it that forms a numerical Jacobian by running five perturbed copies of the simulator in parallel, each snapshotting state, perturbing one input, predicting forward and rewinding. The robot is five cast silicone segments with rigid printed ends, tendon-driven, tracked by markers through an overhead 4K camera.

Outcome

Set-point accuracy of 0.3 mm at the tip, with trajectory tracking typically between 0.6 and 0.8 mm, against a vision system that itself resolves pose to 0.35 mm and slope to 0.005 radians. The model matches FEM to within a few percent on tip deflection across aspect ratios, and its first three natural frequencies sit within about 2 percent. The control loop runs at 2 to 4 Hz, which is a pseudo-static controller's honest limit and the thing I would attack next. Awarded a departmental Research Award.

Robotic charging challenge: reachability-driven arm design

Feb 2023 · Inter-IIT Tech Meet 11.0, Silver Medal

A robot arm that plugs a charger into a car nobody parked carefully. I scored every cell of the arm's task space by how many distinct orientations it could reach that cell in, then used that field to choose link lengths. Reaching the port's position is useless if you cannot arrive along the plug's axis.

Problem

Jaguar Land Rover's brief was an autonomous charging station: find an electric car's charging port with cameras and plug a connector into it. Two things had to be true at once. The arm's geometry had to reach every plausible port pose, because cars park sloppily and port height varies by model. And the motion had to be self-collision-free and slow enough near a customer's car to be safe. Nine days, nine people.

Approach

I described the arm as a parametric table over its link lengths, so changing a link was one edit and everything downstream re-derived. Each link got a collision bounding box measured off the CAD. Then a sweep over the joint space records, for every collision-free configuration, the end-effector pose including its approach axis, producing not a binary reach mask but a count of distinct reachable orientations per task-space cell. With that cheap enough to re-run, changing a link length became a measurement instead of a guess.

Outcome

The submission took the Silver Medal. The characterisation gives a usable task space from roughly 0.4 to 0.8 m from the mount, and the orientation-count field is what drove the link-length change. The repository does not record a before-and-after number for that change, so I am not going to quote one.

A warehouse fleet that was not allowed to know where it was

Jul 2021 – Jan 2022 · Flipkart GRiD 3.0

Flipkart's brief said the robots could not localise themselves: one ceiling camera had to place the whole fleet. That single constraint forced everything, and it was also the thing that never fully worked.

Problem

Build a small-scale version of a sortation fleet and improve its throughput. Each robot had to fit in a six-inch square, carry a cube on a tray that flips to drop it, and take all of its position knowledge from an overhead camera. So: centralised multi-agent planning over robots that cannot sense themselves, with real lens distortion and real timing jitter in between.

Approach

I built the parametric robot model and the Gazebo arena with an overhead camera, and the marker-based estimator that turns detections into fleet poses in grid coordinates. For planning I took an open-source conflict-based search implementation and made it plan for real differential-drive robots: I added heading to the search state so that turning costs time, and widened the conflict test by a timestep so two robots arriving one tick apart in the same cell count as a conflict. On the mechanical side I designed the chassis and the later three-wheel omni-drive revision, and wrote the inverse transform from body velocities to wheel speeds.

Outcome

We reached round two, a physical arena was built and a bot drove on it. The full multi-agent stack worked in simulation. The localisation never fully stabilised: the last commit in the repository is a teammate still fixing the estimator, and the code ends configured for a single robot after scaling down to debug hardware. There is no throughput measurement, which is awkward given throughput was the brief.

Convex MPC for a quadruped, and the QP underneath it

Jan – Apr 2023 · Course project, four-person team

A convex model-predictive controller for a quadruped, with a hand-written active-set QP solver rather than a library call. The interesting part was noticing that most of the constraints were redundant and proving which ones.

Problem

Convex MPC for legged locomotion reduces to solving a quadratic program every control step, over ground reaction forces subject to friction-cone and contact constraints. Written naively the program carries far more constraints than variables, and an active-set solver spends its time on constraints that can never bind.

Approach

I implemented the standard convex MPC formulation for a quadruped over a prediction horizon, then attacked the constraint set directly: a three-stage reduction that takes a system of fifty-odd constraints on twenty-four variables down to roughly twenty-two to twenty-five, including an epsilon-tightened friction cone so the reduced set stays strictly feasible. The QP itself is a hand-written active-set solver, so the reduction translates directly into iterations saved.

Outcome

A working closed-loop model in simulation. I am not going to quote a performance number, because no results were ever saved from it: the deck has no results slide and the repository has no stored trace. What the project actually demonstrates is the constraint analysis, and that stands on its own. The discretisation in the committed code also used an element-wise exponential where the matrix exponential is required, which is corrected but means anything measured before that correction would have been measuring the wrong model.
