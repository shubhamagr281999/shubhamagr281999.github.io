Running a learned model on a robot's NPU

A person-following capability with the detector running on the robot's Hexagon DSP. Detecting people is the easy half. Knowing that the person in frame now is the same person you were following a second ago is the half that decides whether it works.

  • Perception
  • Physical AI
  • Embedded

My part Created the module and wrote nearly all of it: the on-device inference path, the tracker, and the following behaviour.

Problem

Following a person needs a detector fast enough to run continuously on a power-constrained mobile SoC, a way to hold onto the right person across frames when other people walk through, and a motion estimate good enough to keep going when the detector misses.

Approach

A person-landmark network runs on the DSP through the vendor's neural network SDK, with the backend and model both loaded dynamically from config so the model can change without a rebuild, and tensors built by deep-copying the graph's own descriptors so shapes and dtypes follow the model instead of being hard-coded. Detections are thresholded and passed through a hand-written non-maximum suppression. Foot landmarks project to a ground position through the depth image, an HSV histogram gives an appearance model, and association scores squared distance plus a weighted appearance term. A templated, allocation-free Kalman filter carries the target through detection gaps.

Outcome

Shipped as a real capability, with the follow distance, search pattern, extrapolation window and association weighting all configured rather than compiled in. Because the detector sits behind an interface with a dummy implementation, the tracking and behaviour layers run and are testable with no DSP and no robot present.

Getting a network onto the DSP

The detector runs on the SoC's digital signal processor through the vendor SDK. Both the backend and the model are loaded at runtime as shared objects named in configuration, so swapping a model is a config change rather than a rebuild.

The part that matters for correctness is that nothing about the model is hard-coded. Input and output tensors are constructed by deep-copying the graph's own tensor descriptors and allocating from them, with sizes and data types derived from the graph. The model's expected input resolution is read out of the graph and returned to the caller, so preprocessing follows the model rather than assuming it.

Per-node profiling walks the SDK's profiling event tree, which is how you find out that a layer has quietly fallen back from the DSP to the CPU. Without that you only see the aggregate slowdown and guess.

The filter was tracking the wrong thing

This is the part I would want to be asked about.

The estimator initially tracked the derived goal pose rather than the person. That works until it doesn't. The goal is a function of the target, the robot's own pose and the follow distance, so filtering it mixes the person's motion with the robot's motion and with the geometry. The estimate degrades exactly when the robot is manoeuvring, which is exactly when you need it.

The correction was to track the person and let goal generation become a pure function of a properly estimated target. It is a design error, found and fixed, and the branch history still shows it.

The filter itself is written from scratch, templated on state and measurement dimension so all the matrices are compile-time sized and the estimator never allocates. It exposes both predict-and-correct and predict-only estimation, and the predict-only path is the one that carries the target through a detection gap for a bounded window before the robot gives up and rotates to search.

Not losing the person in a crowd

Nearest-neighbour association swaps targets the moment somebody walks closer to the robot than the person it is following. That is not an edge case, it is a corridor.

So the association cost is squared distance plus a weighted appearance term from an HSV histogram of the detection box, compared by correlation against a stored model of the target, with detections below a similarity threshold rejected outright. The weighting is a tunable parameter rather than a constant because the right trade-off between same-place and same-clothing depends on the environment.

The unglamorous half is depth. Both feet, one foot, neither foot, and physically implausible separations between them all happen constantly. If the two feet are a plausible distance apart their midpoint is the ground position; if not, the foot nearer the last known position is trusted and the other discarded as a bad reading; if only one has finite depth, that one is used. Every branch has to produce something sane or the track dies, and that logic is most of what makes the module work.

Why this is the answer to one specific interview question

"Can you get a learned model running on a robot?" is the question an embodied-AI team actually needs answered, and it is usually answered with a plan.

Here the conversion and deployment path onto the DSP and the runtime that consumes it were built by the same person, and the result shipped. That is the whole point of including this project: it makes the rest of my model work concrete rather than aspirational.
