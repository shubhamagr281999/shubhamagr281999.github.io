The gap this fills

A team wants vision-language-action policies running on its own bimanual arms. The weights and the training code are open source, so the interesting problems are not the model ones. They are: how do you turn a pile of teleoperation recordings into a training set that will not quietly poison the run, how do you evaluate a candidate policy in a way that means anything, and how do you get the same policy onto real hardware without a second codebase.

I built all three, and the useful thing is that they inform each other. The curation tool checks for a failure mode I only knew about because I had traced the model's normalisation code.

Making a slow model safe to control with

Policy inference is far slower than a control tick. The obvious structure, infer then act, either stalls the controller or drags it down to the model's rate. Neither is acceptable on an arm.

The runner instead uses four wall-clock-paced threads that exchange latest values and never block on a slower peer. The backend steps physics and renders cameras into an immutable image bundle that is swapped without locking. Inference runs asynchronously and its result is drained on a later tick. A missing action chunk means hold the last setpoint rather than emit a discontinuity.

The result is the design goal: a slow model costs smoothness, not correctness.

The delta command that walked the arm across the table

The Cartesian impedance controller takes a six-dimensional world-frame delta end-effector command. The obvious implementation composes that delta with the current pose on every tick, which silently ratchets the target forward for as long as the command is held, so one commanded step walks the arm across the workspace.

The fix is to compose once, on a fresh action, into an absolute target, and track that stored target on held ticks. It is invisible until the arm is moving and obvious afterwards, which is exactly why it is documented in the class rather than left as a comment.

The operational-space maths behind it runs as a C++ and Eigen extension: task-space inertia with decoupled position and orientation, a nullspace term, damping-ratio-derived gains. The bindings are deliberately zero-copy, with row-major references, because Python hands over C-contiguous slices and a column-major reference would force a silent transposing copy on every control step.

Collision checking a robot that is always touching itself

The safety gate writes a candidate command into a private replica of the workspace and asks whether the arm would touch itself or the scene. Naively this rejects everything, because collision geometry is a coarse over-approximation and an arm registers contacts at rest that the hardware does not have.

So at each episode start the layer measures the arm's actual post-reset contacts and exempts each pair only up to its own measured depth, plus a small margin. A pair that later penetrates deeper is still a violation, and those links stay live rather than being switched off for the run. The exempt set is logged every episode so the exemption never becomes invisible.

Reading the model, then tooling what I found

I traced both candidate architectures operation by operation and checked them against live instrumented runs.

One of them turns out not to decode at all. It runs a single non-autoregressive pass over a fixed-length sequence whose action slots are zeroed, so at the first layer those slots have queries, keys and values all exactly zero and their attention is a uniform average over everything visible. The action slots are pure positional queries and all content arrives through attention. That one observation explains most of the otherwise strange code on the path. I also measured that the action head's two residual blocks move the representation by about 2.6 percent, because the residual branch ends in a ReLU and most of its units are dead.

The part that paid off immediately was duller. Fine-tuning on new episodes while keeping the original dataset's normalisation statistics means any out-of-range value normalises outside the range the model was trained on, and the normalisation code does not clip, so nothing downstream notices. I found it reading the code, then built the guard for it into the curation tool: load a reference statistics file, check the current selection against whichever bound matches how the model was trained, and name that bound in every message, because the same data flags none of a hundred episodes under one bound and all hundred under another.

The error that pointed at the wrong place

Evaluation runs started dying with a CUDA error reporting no kernel image available, about four hundred lines into a script. Not at model load, which is where anyone would look first.

The cause was that the project pins a torch version whose compiled architecture list stops well short of the evaluation box's GPU generation. It surfaces late because moving a model to a device is a pure memory copy. Nothing executes a kernel until the first real operation, so the failure appears at the first compute call rather than at the incompatibility that caused it, and nothing in the repository checks GPU capability at start-up.

I wrote a standalone diagnostic that prints the compiled architecture list against each GPU, tries three trivial kernels, and surveys every environment's build, so the next person spends a minute on it instead of a day.
