Production autonomy stack for an indoor mobile robot

Three years on one robot, across every layer of it: the sysfs GPIO driver that moves the wheels, the shared-memory bus that carries the odometry, and the TSDF mapper and planners that decide where to go. The mapping backend was replaced mid-life without touching the planners.

The span

The claim worth making about this project is not any single algorithm. It is that the same person wrote the driver that moves the wheels and the mapper that decides where they should go, and that those layers were designed to fit each other.

At the board level that meant a Yocto layer for the SoC, Dockerised aarch64 cross-compilation, device-tree patches and A/B image deployment. Above it, a hardware abstraction layer: sysfs GPIO and hardware PWM, quadrature encoders, motor and servo drivers, a small co-processor firmware for PWM, an IMU client. Then a templated PID drive system with anti-windup and differential-drive odometry that fuses IMU yaw with timestamp interpolation.

Between the embedded layer and the autonomy layer sits a publish/subscribe and service bus built on shared memory rather than ROS, with typed channels, interprocess mutexes and condition variables, and custom serialisation. A systemd service and watchdog keep the processes alive in the field.

Replacing the map without breaking the planners

The first mapping design was a moving local volume feeding a two-dimensional global grid. The local map is a ring buffer sized to a power of two so the volume translates with the robot without copying data, which reduces the index arithmetic to bit operations. It worked, but it could not support persistence or loop closure.

The replacement is a life-long backend built essentially from scratch: truncated signed distance function submaps with trilinear interpolation and the ability to fuse and un-fuse a submap, a hybrid voxel that packs the distance value, occupancy state and Euclidean distance field together so one block traversal serves surface reconstruction, occupancy and clearance queries, and a pose-anchored submap collection that consumes optimised poses from the team's SLAM and rebuilds its spatial hash when they arrive. Distance fields come from the Felzenszwalb lower-envelope transform, refactored into a separable one-dimensional pass for speed.

Swapping a mapping backend underneath a working planning stack is the kind of change that usually becomes a rewrite. It did not here, because the mapper sat behind a common interface chosen at compile time. The same trick applies to the communication layer, where identical algorithm code runs against either ROS topics or the shared-memory bus, so the stack develops on a desktop with ROS tooling and deploys on target without ROS.

Why the planner is fast

D* Lite was chosen over A* because the map changes continuously and prior search results should be repaired rather than discarded. A* was implemented first, optimised, measured, and then archived.

But the algorithm is not what makes it fast. The published description tells you what to compute. It does not tell you that the open list needs an augmented key to live in an ordered map, because D* Lite keys are not unique, or that node lookup needs a hand-written bijective two-to-one-dimensional hash to stay constant time on the hot path. Those two structures are the difference between a planner that keeps up with a moving map and one that does not.

Obstacle distance from the distance field folds into edge cost, so paths prefer clearance instead of hugging walls, and a new path only replaces the current one if it differs by more than a threshold, which stops the visible flapping you otherwise get when the map updates.

The local planner samples a velocity window admissible under the robot's acceleration limits, rolls each candidate out and scores it. On top of it sits a behaviour layer: stuck detection with recovery, retreat on contact, heading alignment at start and goal, and obstacle inflation that scales with current speed, so the robot is conservative when it is moving fast and permissive when it is crawling.

Glass

A depth camera cannot see a glass partition, and an indoor robot meets them constantly. The cheapest correct sensor for a transparent wall turns out to be having touched it, so bump-sensor contacts are fused into the map as occupied voxels at the computed collision point and the distance field is recomputed around them.

It is an unglamorous fix and it is the kind of thing that decides whether a robot survives a real building.

Measuring instead of asserting

Performance regressions are invisible unless something is watching for them. I wrote an in-house profiler that times instrumented functions into a CSV, then wired it into CI as a comparison rather than a report: the pipeline downloads the baseline profiler data from the package registry and plots the current change against it as a build artifact.

That is a materially harder thing to build than a test suite, and it is the reason specific optimisations here, the separable distance transform, single-pass raycasting, reduced hash lookups, avoided allocations in the frontier scoring loop, can be stated as results rather than intentions.
